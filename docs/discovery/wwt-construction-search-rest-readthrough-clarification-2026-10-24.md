# Wheelwright construction search — REST/query/read-through clarification

**Date:** October 24, 2026. **Standing:** Principal Product/architectural direction following the October 24 walkthrough and Codex read-only reconciliation; Category D clarification checkpoint, not accepted OAS or implementation authorization. The earlier Codex `/v2/construction-searches` resource design is **rejected as the preferred initial shape**, not proof that every asynchronous resource is forbidden. Kiro excluded.

**Prior checkpoint:** [Construction search walkthrough](wwt-construction-search-product-walkthrough-2026-10-24.md) at `deb301fa3d89e22c6b79f132c98b259da3f36e92`. Preserve its Product conclusions on ephemeral Construction values, backend authority, conversational narrowing, funnel/table, off-hours market evidence, optional saving and conditional progressive UX.

## Principal corrections

1. **Query-oriented REST, not a search-execution registry.** Principal rejected the three proposed `/v2/construction-searches` endpoints: “ugh... no. /v2/chains?query params”. Begin with `GET /v2/chains` and clear typed query parameters such as underlying, DTE range, risk constraints, supported sorting/preferences and evidence scope. The exact path, names and semantics remain subject to contract fit, but do **not** reinstate managed search identity as the presumed default. Normal queries return evaluated ephemeral results; future durable saved searches can be additive if Product value emerges.
2. **Projections.** Principal: “in addition to clear query parameters, you can also have projections.” Separate selection/constraints/comparison criteria from which domain fields and details the client requests. Same evidence and criteria must produce equivalent financial conclusions across projections; presentation/typography remain client-owned. Evaluate against current v2 projection conventions. An illustrative `projection=summary` versus `projection=full` is not ratification of names or of a special progress projection.
3. **HTTP conventions first.** Reuse pagination, collection links, next hrefs, response metadata, appropriate 202 and retry guidance, conditional GET/ETag and caching only as justified by concrete cases. Incomplete data can allow progressive responses if inexpensive; do not force a new lifecycle framework. If long work genuinely needs temporary operation state, justify the narrowest HTTP arrangement without automatic durable history. GET safety must be preserved; no brokerage trading effects.
4. **Client/server separation and transparent read-through.** Principal: “remember the REST principle about clients and servers. and remember that conceptually ww v2 is a cache of sorts. and readthrough caching is a known capability”; also “the notion that the client doesn't have to know if it's talking to a proxy”. Clients ask a Wheelwright domain question, not separately orchestrate cache lookup versus acquisition. Backend may satisfy it from qualified retained evidence or acquire missing evidence through **existing authorized provider controls**; request and result meanings remain stable across sourcing. GET may entail internal cache fill while remaining safe in HTTP's domain-action sense. Do not claim this automatically overrides v2's existing acquisition grants, FORCE semantics, rate controls, or historically provider-free read contracts. Design must explicitly reconcile these.
5. **Analogy limit.** Principal: “sure, ww isn't squid”. Wheelwright is a domain/evidence appliance with normalization, policy and financial conclusions, not a generic HTTP proxy or an invitation to construct caching infrastructure. Client transparency does not conceal source provenance, evidence clocks or meaningful limitations.
6. **Thin MCP.** Talk/MCP maps conversational intent to query parameters and requested projections, follows HTTP affordances when needed, and presents backend facts. It neither assembles option chains nor owns eligibility, Greeks, payoff, financial ranking, provider credentials or evidence admission. REST clients other than MCP receive equivalent domain conclusions.
7. **Future optionality.** Ordinary searches remain ephemeral. If demand later justifies saved definitions or retained evaluations, add independently justified durable capabilities without forcing persistence into every initial request. Explicit reproducibility semantics can precede permanent history.
8. **Operator UX.** Funnel counts + compact distinct-construction comparison table remain preferred. Progressive results are desirable only if cheap; the contract should not mandate intricate orchestration. Use qualified latest open-session evidence outside market hours and preserve truthful provider qualification without repetitive disclaimers.

## Design questions for the next Codex pass

- Does `/v2/chains` adequately name a collection query returning evaluated constructions? If a semantic conflict exists, demonstrate it against governing API v2 contracts and propose the smallest faithful alternative rather than quietly restoring `/v2/construction-searches`.
- Can standard GET/query/projection semantics support the required candidate evaluation and optional progressive behavior, with backend-only evidence selection and side effects limited to authorized cache fill?
- How are typed parameters, pagination, projection equivalence, snapshot/evidence consistency, ETags, authorization, error responses and conditional acquisition specified with minimal invention?
- What smallest representative OAS-facing request/response and falsification demonstrate this, including retained cache hit, authorized read-through miss, denied acquisition, market-closed evaluation, and preference refinement without acquisition?
