# EA on a Page ↔ Wheelwright Product/environment crosswalk — idea intake

**Captured:** October 23, 2026. **Standing:** Principal idea/intake only, not a mandate to implement, migrate, reclassify authority, or create any new artifact.

## Principal intent (verbatim excerpts)

- “what would be nice is if we had some mapping of our in-place doc structure to the standard ‘ea on a page’ taxonomy. no shoehorning required.”
- “yes, i don't want to migrate anything. i want a map if you will. persist this idea.”
- Clarifying context: “we're not using the kotusev model for EA. we're using it as a reference taxonomy for a product/environment”; “we're adapting it for our needs”; “there's lots of good stuff we have: the ontology, the roadmap, the PLs, the LVT. these are all potential great fits for the taxonomy.”

## Idea

Maintain an optional, navigational, **many-to-many crosswalk** between the repository's **existing in-place knowledge/document structure** and Kotusev's *Enterprise Architecture Artifacts on a Page* v3.0 reference taxonomy, **adapted to Wheelwright as a Product and its technical environment**, not as an enterprise-architecture methodology.

- Start from the actual subject-owned ontology/domain knowledge, roadmap, Lean Value Tree, parking lots, ADRs, principles, design notes, API contracts, code/runtime witnesses and question inventory.
- Map **both directions**: an EA-on-a-Page artifact purpose can point to multiple current Wheelwright sources; any Wheelwright source can serve multiple artifact purposes—or none.
- Illustrative *candidates*, not asserted classifications: ontology ↔ conceptual domain/data modeling; LVT and roadmap ↔ goals/roadmaps; questions ↔ capability models; system/runtime composition ↔ system portfolio models, landscape diagrams, technology inventories; principles/ADRs/mandates ↔ IT principles, guidelines and design decisions; change investigations ↔ options/overviews/designs.
- Preserve each source's location, canonical owner, authority classification, maturity/status, date, provenance and actual applicability. A link does **not** promote discovery evidence to Product authority.
- Mark relationships honestly: direct, partial, distributed, derivable, uncertain, not applicable or unmapped. No forced mappings, missing-tile backlog, duplicate registries or folder migration.
- Reuse the [October 18 Kotusev v3 title verification](knowledge-survey-2026-10-18/kotusev-v3-name-verification.md) and prior knowledge architecture reconciliation rather than repeating taxonomy research. Earlier survey verified 34 named tiles; treat classification nuance faithfully and do not enforce a document-per-tile scheme.
- Evolve the map incrementally as operator questions produce working capabilities and new technical evidence, without slowing question delivery.
