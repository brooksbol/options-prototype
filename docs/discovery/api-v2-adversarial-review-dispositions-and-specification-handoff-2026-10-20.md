## Architectural acceptance boundary

Wheelwright **API v2 is a Product in its own right**: clean financial ontology, independent resource identities, coherent resource topology and navigation, extensibility, scalability, usability, and multi-client financial fidelity govern. The authoritative backend interprets broker evidence; each client presents it. The `tt live` accepted story is a concrete proof benchmark but one-row CLI glyph fidelity is intentionally lossy; exact financial math/geometry remains obtainable by rich/agentic clients. Alpha v2 imposes **no external backwards-compatibility commitment**. Reject sunk-cost preservation of accidental current semantics, but preserve authoritative evidence, useful behavior and financial integrity. The existing holistic API principle was updated by Principal clarification at commit `405c964b7ab493851cff765df0576a33c94e7ce1`.

## Major finding dispositions

1. **Enduring Position identity — Product rule selected; ingestion remains separate.** A Wheelwright Position resource has its *own unique GUID*, not a broker series/instrument ID. Its representation may mutate while open; `CLOSED` is terminal. A subsequent opening creates a new Position GUID even if broker Account and option-series ID are identical. Broker IDs are source attributes, not unique Position keys. A Construction instance is write-once and Position points to the current instance. Unobserved close/reopen does not magically become known; reconciliation and evidence qualification are independent of resource design. This is a Principal-selected *working rule* for proposed v2; `ASSIM-0002` and the maintained Position owner still need authorized reconciliation, especially scope split/recombine/Operating Regime. No universal lifecycle engine is implied.
2. **Account-wide allocation/conservation — valid engineering/reconciliation requirement, not a new ontology.** Broker-reported inventory and aggregate Construction allocations of source quantity must reconcile across *all* affected Positions, not only within individual trees. Example: broker 250 shares; independent Constructions each claim 150: 300 allocated is invalid. Preserve source inventory, flag discrepancy, mark affected conclusions incomplete and surface remediation. Differentiate data-quality gaps from software double counting; do not force balances, invent ledger events, invent available collateral, or infer cost-lot attribution. Engineering must test global conservation and evidence-qualified basis.
3. **Incompatible recognition — validation correction; no forced match.** Enforce multiplier, deliverable, currency and strike constraints (including reverse Jade Lizard). If structure doesn't pattern-match or terms are incompatible, retain constituent composition and facts in an **unclassified Construction**. Distinguish absent *name* from unavailable *economics*: generic compatible leg math may still evaluate exact payoff; incompatible horizons/missing terms yield qualified incomplete calculations. Never fabricate labels or drop inventory. Future operator `give it a name` is an out-of-scope enhancement; a user label does not ratify a mathematical model.
4. **v2 insufficient for accepted `tt live` — engineering source-coverage gap, conditionally architecture-relevant.** Working `tt live` demonstrates the bounded capability. Engineering must map each accepted story field to source evidence, v2 admission/normalization, backend interpretation and unknown/warning behavior. New domain design needed only if some field cannot be faithfully expressed. Current v2 null values and lack of working Order/option-mark evidence are not automatically missing domain concepts. Preserve the accepted story's qualification limits; no trading automation.
5. **Current v2 semantics differ — NO alpha backwards-compatibility requirement.** Principal explicitly rejects sunk-cost logic. Reuse Account-nested transactions, Artifacts and existing routes only if useful to clean target API Product. Current observed-inventory `positionId` semantics may be replaced by the independent Position GUID contract. Engineering must coherently implement and test selected target semantics and protect real financial evidence; no blanket migration compatibility veto.

## Moderate and other findings

- **Historical model reproducibility:** Construction **Models are versioned and write-once**, as are Construction instances. Each instance links to the *exact immutable Model version* used for interpretation. Revising the Model creates a different version, never mutates old interpretation. Evidence correction/reinterpretation and actual held-exposure change must remain distinguishable. Version URI shape is engineering's choice.
- **Forced recognition:** Resolved by unclassified constituent fallback above. A Construction exists even when no validated named model applies.
- **Execution requirement:** Current holdings are established by broker holdings evidence, not by mandatory fill history; snapshots alone do not prove causal Executions. Root `/v2/executions` remains deliberately open/not required. Preserve actual broker-reported fills, Orders and transactions when available without inventing events.
- **Warnings and authorization through projections:** Existing semantic rule stands. Warning status and provenance must accompany displayed incomplete results for any projection; token-root User and authorized Account scope applies to links, collections, expansions and historical/audit reads. Test concrete leakage and false-precision cases; no separate warning subsystem required.
- **Unicode Broken-Wing tails:** Accepted intentional one-row presentation loss. Full economic tail heights and geometry in backend/API must remain exact.
- **Portfolio:** Still alpha-stage exploratory; may be deferred, or reviewers may recommend minimal grouping. Do not silently equate Account membership or Position grouping with Operating Regime, capital availability or custodial semantics.

## Remaining candidate API topology and resource semantics

Working conceptual family: Users, Accounts, Positions, Constructions and versioned Models, Orders, broker-sourced market observations, Transactions where justified, imports/Artifacts and selected Audit; Brokerages and derivative Contract/Instrument families where independently meaningful. Position default response includes evidence-qualified current backend financial summary and links; collections support client-selected URI/summary/expanded projections using conventional engineering mechanics. Position history via selective audit; Construction history via immutable predecessor links. Public imports and internal parsers provisionally preferred. `ww pull` is the refresh precedent; sync operation identity remains evidence-dependent. Financial evaluation stays in Position representations provisionally, reviewing broker-reported values versus derivations. HTTP errors distinct from valid but incomplete financial conclusions. Brokerage-specific IDs may recur across independently identified Wheelwright resources.
