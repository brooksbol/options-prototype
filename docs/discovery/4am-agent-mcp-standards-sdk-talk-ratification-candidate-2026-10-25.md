# 4AM reconciliation candidate — agent architecture standards and SDK-based Talk

**Recorded:** October 25, 2026
**Standing:** Principal-directed architectural direction and **candidate reconciliation for 4AM ratification**. NOT ratified standards, implementation authorization, accepted solution design, code acceptance, or a claimed actor endorsement.
**Prior context:** PL-MCP-01, October 25 industry standards intake, independent Codex and Kiro investigations and reciprocal reviews, independent Muse external research.

## Principal direction (recorded verbatim in substance)

1. Establish standards sufficiently clear to direct agentic engineering without strictly prescribing every implementation detail.
2. Ground those standards in independently verified industry specifications, well-architected guidance and agent-tool engineering practices.
3. Set aside the current one-off bespoke Talk experiment, at least for now. Preserve its evidence, source/installed status and useful lessons; do not erase or silently decommission anything.
4. Develop **a new, self-contained Wheelwright Talk based on the OpenAI Agents SDK**, as explicit Principal technology direction. Do not silently substitute custom Responses orchestration. Exact SDK version, configuration, implementation, migration, acceptance and deployment remain separate design/authorization questions.
5. Produce this reconciliation for a genuine 4AM adversarial ratification process.
6. Persist **each actor's own ratification/disposition** separately with source, evidence, scope, disagreements and actual authority. Codex and Kiro must independently report; neither their prior investigations nor this document count as their ratification. Muse is external research, not a Wheelwright ratifying actor. Principal acceptance remains the final authority for architectural ratification.

## Reconciliation: existing authority and genuinely new commitments

Existing authority already covers question-driven Product development; backend-owned financial semantics and evidence; one v2 API with many clients; authorized user/data boundaries; complexity earned, recover/reuse/compose before invent; versioned ADR/knowledge ownership; graduated architectural fitness controls. Do not mint duplicates.

**New Principal direction requiring precise architectural disposition:** an SDK-based new Talk and a pause on further bespoke one-off Talk development. The pause is a sequencing directive, not acceptance/rejection of candidate code or permission to mutate installations. Existing original MCP-learning purpose and host independence remain relevant; using an SDK in one host does not mandate that other hosts use the SDK or MCP.

**Candidate operational standards for ratification review** (industry sources are support, not Wheelwright authority):
- **Decision determinacy:** for a consequential architectural choice, implementing actors recover binding precedents, identify viable native/framework and custom alternatives, document constraints and trade-offs, and identify the accountable decision authority before a durable divergence. Do not prescribe a chosen pattern where justified alternatives exist.
- **Framework leverage:** default to reviewing available supported framework mechanisms before reimplementing generic agent loops, sessions, tool discovery, tracing or recovery; custom behavior is permitted with evidence of need, privacy, security, economics or Product fit. The Principal's SDK choice for *new Talk* is a scoped technology directive, not a general vendor mandate.
- **Reusable capability boundary:** backend owns authoritative financial state, evidence and governed conclusions; MCP faithfully exposes independently meaningful capabilities without duplicating calculations; SDK host owns generic conversational execution, tool admission and context/presentation. Do not mandate one tool per question or speculative tool catalogs.
- **Trusted semantics and disclosure:** authorization and financial claims are not enforced by prompts/schema alone. Trustworthy financial assertions must preserve backend claim identity, subject, provenance and qualifications. Whether free conversational arithmetic/financial interpretation is allowed and the applicable model disclosure profile are open Product decisions to resolve before relevant acceptance.
- **Observable fitness:** evaluate real operator questions through bounded API/MCP/host specimens; preserve useful errors, correlation, partial evidence and actual subject continuity; test negative security/semantic cases. Controls begin observational and earn promotion through the existing Technology Quality Constitution; no automatic CI gates.

Potential falsifiers: actor cannot tell who owns an architectural decision; two actors independently make durable incompatible choices without flagging missing authority; new tool requires question-specific host source code; API v2 422 loses safe problem identity or request correlation; a model presents an indicative credit as a confirmed fill or wrong financial probability; confidential result is exported through tracing/compaction; conversation narration fails and otherwise established evidence disappears; new process delays operator feedback without measurable gain.

## Industry-source basis and limits

- MCP architecture and tools, applicable pinned protocol revision (including 2026-07-28): https://modelcontextprotocol.io/specification/2026-07-28/architecture and https://modelcontextprotocol.io/specification/2026-07-28/server/tools
- OpenAI Agents SDK JavaScript (MCP, sessions, tracing, guardrails): https://openai.github.io/openai-agents-js/
- Anthropic, *Writing effective tools for agents*: https://www.anthropic.com/engineering/writing-tools-for-agents
- AWS Agentic AI Lens: https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentic-ai-lens.html
- Azure Well-Architected AI workloads: https://learn.microsoft.com/en-us/azure/well-architected/ai/get-started
- Muse research: external industry evidence with documented errors/uncertainties. Cross-review corrections include current MCP trace metadata and Origin requirements, JS rather than Python SDK applicability, difference between conditional selection and overall tool retrieval performance, and no automatic requirement for separate gateway processes, registry, second consumer or mandatory fitness gates.

No external source alone dictates the chosen Talk implementation. The SDK choice is Principal direction. SDK selection does not prove conformance to privacy or financial-authority boundaries; default SDK tracing/compaction/session egress requires explicit evaluation. Native SDK must not be mistaken for an authoritative financial engine.

## 4AM ratification procedure and evidence

Each actor should deliver a separate dated disposition of each material proposition: RATIFY / AMEND / DEFER / REJECT / NO NEW STANDARD, distinguish verification and judgment, and identify contrary evidence. Each record should cite its inspected repo SHA, real source locations, subject authority and any conflicts. Persist each disposition under its own provenance (not as an invented collective consensus). Do not resolve these by actor inference.
