# API v2 foundational Portfolio — adversarial review candidate snapshot (2026-10-20)

**Standing:** Principal-directed read-only adversarial-review briefing, a Category D discussion snapshot. This is NOT an operative OpenAPI spec, an independent authority override, a Product ratification of every candidate, or authorization to implement. Repository A–F precedence, maintained knowledge owners, governing ADRs, assimilation obligations and real broker evidence prevail. Reviewers must independently bootstrap and discover exact authority rather than treating this snapshot as a proof.

## Objective and scope

Deliver the foundational Portfolio domain through API v2 so that `ww live` can reproduce accepted `tt live` human-oriented, single-row trade-story experience with all financial interpretation in the backend, while `ww positions` offers full inventory and other clients (including agents and richer UIs) retrieve detailed faithful evidence. Focus on Accounts, instruments/contracts, Positions, Construction Models/instances, held inventory/allocations, Orders, market evidence/evaluation, transactions when supported, imports/refresh and API navigation. Exclude implementing Strategy/Operating Regime, margin, brokerage reimplementation, trading/Order submission, web/mobile-specific UX, and v1 retrofits.

## Working candidate, agreed with Principal

1. **Constructions:** every Position has a Construction; write-once Construction instances with broker Account and Position association. Reusable declarative Construction Models specify typed leaves, recursive composition, recognition constraints and exact economic/payoff math; shapes must be derived, not hardcoded model glyphs. `GET /v2/constructions`, `/{constructionId}`, `/models`, `/models/{modelId}` are the candidate URI family. Position points to currently applicable instance; instance may hyperlink to predecessor, yielding navigable immutable history. Position identity has mutable state, but termination/reopening boundary remains open (`ASSIM-0002`).
2. **Inventory/conservation:** cash, owned shares, option obligations and coverage/collateral must retain measured quantity, provenance, cost and Account attribution when decomposed into Positions and recomposed. No double-counting, collateral is not an inferred free-balance assertion. Correct financial and exposure semantics must survive decomposition/recomposition.
3. **Orders:** broker-directed instructions initiated by trader, observed by Wheelwright; independent of held Positions. Open/unfilled/expired/canceled closing Orders do not modify exposure. Wheelwright is NOT an Order-generation/submission service. Evidence-backed association only (ADR-016). The GTD-at-21-DTE notification tactic is an *untested hypothesis*, not proven notification or exit behavior.
4. **Position response:** canonical links and scoped identity + current state; backend-evaluated, evidence-qualified financial summary by default, with links for constituents, related Orders, facts, provenance and history. Keep detailed broker records under their own authority; Position is composition point, not a god resource.
5. **Collections:** client-selectable projection may return URIs, summaries, or expanded payloads. Filtering, sorting, pagination, syntax and defaults delegated to engineering using sound industry conventions; preserve authorization and truth across projections.
6. **Evidence warnings:** structured data identifies missing/stale/conflicting evidence, affected calculations, reliable surviving facts, explicit INCOMPLETE labels and operator-actionable remediation. A current quote is not an implicit historical quote. An import or pull can succeed but evaluations remain incomplete; HTTP/resource success is separate from financial status.
7. **Evaluations:** current Position evaluations embedded in Position representations/projections as initial preference; quotes/market observations are sourced evidence, distinct from derived calculations, with source timestamps. Review which values Fidelity/tastytrade already report and whether any evaluation identity warrants its own resource. API must preserve exact financial geometry and numeric economics for richer clients. **One-row Unicode/ASCII `ww live` visualization is intentionally lossy; this is not a defect.** Its loss must never degrade the underlying domain or API data, including unequal broken-wing tail heights.
8. **Transactions:** provisionally `/v2/transactions`, broker records authoritative, normalize only for supported financial meaning and trace to source. Do not invent complete activity or an Execution record from changing Position snapshots; do not rebuild brokerage accounting systems.
9. **Imports and parsers:** public import/upload outcome resources, broker-format parsers internal by default. Provenance, ambiguity, repeat/duplicate safety, partial acceptance and stronger guardrails open for engineering challenge.
10. **Instruments/contracts:** reliable source identity may use broker-qualified compound key, such as `(brokerId, brokerContractId)`. Preserve strike, expiry, multiplier, currency, deliverables and adjustments needed for economics; do not presuppose a universal cross-broker master. Whether derivative Contract warrants separate family versus specialized Instrument is a review question.
11. **Authorization:** user is token-root principal. All user-specific resources must associate with authorized User or Account; independently routed Position/Construction/Order/Transaction links and expanded collections cannot bypass Account authorization. Shared reference models need not be user-specific. No premature grants/IAM product.
12. **Audit:** optionally expose immutable audit records for mutable resources worth tracking, e.g. `/v2/positions/{id}/audit` and `.../audit/{auditId}`. Audit is Wheelwright retained state/observations, not a synthetic broker activity ledger; separate from Construction's immutable predecessor chain. No universal `asOf` API mandate or separate history systems.
13. **Refresh:** `ww pull` is the accepted operational discovery precedent. Account-level sync/status favored only provisionally; actual workflow may justify a dedicated operation record. Evidence freshness differs per Account and per evaluation; failed refresh need not invalidate retained facts.
14. **Errors:** standard HTTP semantics and consistent structured problems; resource returned with evidence warnings when valid but incompletely evaluated, and operational partial outcome reported separately. Error-schema minutiae delegated to engineering.

## Deliberately open — not ratified

- **Execution:** Do broker evidence and real client needs justify an independent first-class Execution resource? Broker data may expose open Orders and contract positions without complete fills. Investigate both inclusion and omission. Do not make `/v2/executions` mandatory by assumption.
- **Portfolio:** alpha-stage exploration and boundary with Strategy/Regime. Do not preselect Account-membership or Position-membership; request minimum required functionality and alternative suggestions; does foundational v2 need Portfolio beyond Account at all?
- **Position lifecycle:** exact identity through full close/reopen; `ASSIM-0002` PENDING. Avoid treating write-once Construction history as definitive solution to all lifecycle cases.
- **Broker evaluation coverage**, **sync operation identity**, **import guardrails**, **Contract/Instrument topology**, and **Transaction justification** are provisional pending actual repository and source testing.
- **Construction experiment:** local Codex branch `codex/construction-geometry-2026-10-20` at reported `5bab2195504a0d49b2d3ff37743aa7afe7dd100f` NOT verified on remote. Reported 39 models, 33 passing harness tests, 15 existing tests, 321 spot cases, 33 accepted counterexamples; six mixed-expiry refusals. Proposed validation fixes for multiplier/deliverable, currency and reverse Jade Lizard strike ordering. Exact-turn marker / classification overlaps open for review; unequal-tail Unicode loss accepted only as projection loss. See `docs/discovery/construction-geometry-codex-handoff-checkpoint-2026-10-20.md`.
