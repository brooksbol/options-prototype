## 3. Minimal amendments recommended, not applied to the common candidate

### A. Make framework leverage checkable without prescribing all code

Before introducing equivalent generic execution, session, discovery, tracing or recovery machinery, the implementing actor must identify the selected framework release's applicable native facility, the concrete unmet requirement, and the smallest justified extension. Keep this rationale and independent falsifier in the existing work-item/design evidence, not a new form or registry. If no facility is needed, record that bounded choice rather than enabling it speculatively.

For new Talk, SDK execution facilities must actually own the general agent run loop. Importing the SDK around a replacement custom Responses loop is not conformance. SDK-supported hooks/adapters and host-owned UI, credential isolation, cancellation/resource budgets, evidence rendering and policy enforcement remain permissible. A material departure from the selected framework direction returns to its decision owner; routine implementation choices do not.

Verification: inspect the actual execution path and exercise a bounded multi-turn specimen with a failed tool call and a useful non-tool response. Dependency presence alone is not proof. This would expose historical exact-tool/closed-routing behavior if that behavior were carried forward; it cannot guarantee that prose standards prevent drift without actual checks and independent evidence.

### B. Define reusable capability transport at the semantic boundary

Admitted tools must be discovered/described using their supported contracts; configuration/policy may restrict admission, while backend authorization independently enforces every request. Do not maintain a second manually copied capability schema or question-to-tool router without a demonstrated necessity and explicit scope. A new question must first attempt authorized composition; a backend capability, evidence improvement, presentation change, Product clarification or no implementation can be the correct response.

Preserve meaningful outcomes and safe problem identity, subject, qualifications and correlation across API → MCP → host; do not erase a validation refusal into “connection failed.” Redact private diagnostic content rather than flattening every failure. Correlation requires an implemented relationship between trace context and backend request identity, not identical IDs everywhere.

The falsifier is **new capability requires bespoke conversational selection/routing or duplicated financial logic**, not “any host source edit.” New rendering, supported contract evolution, security policy and packaging can legitimately require work. Selection/discovery alone does not demonstrate execution or useful portability. Independently meaningful does not mean speculative universal tools or only fine-grained endpoint wrappers.

### C. Specify the financial output guarantee before exercising that financial scope

Require traceability of an authoritative displayed assertion to the backend-established subject and meaning, preserving units/currency, economic role, source/valuation time, evidence status and material qualifications where applicable. Use existing resource/result identities or scoped locators where sufficient; do not mandate a universal claim format.

Model-generated text cannot establish financial authority by containing allowed numbers, citing a result, passing JSON validation, being labeled “derived,” or receiving another model's approval. A correct table does not authorize contradictory surrounding prose. Qualitative claims such as “safe,” “available,” “you should close,” or “this is governed inventory” need the same appropriate authority as numeric claims.

The solution must distinguish authoritative financial presentation from any permitted hypothetical/model interpretation and state the actual guarantee. If the promised guarantee is deterministic semantic authority, enforce it at a trusted presentation/calculation boundary; finite statistical narration checks cannot be described as that guarantee. No particular rendering technology, DSL, blind-model architecture or per-question verifier is mandated. Independent judgment must assess the remaining semantic coverage.

Falsifiers: reward/risk 77% restated as probability; maximum loss restated as profit using the genuine number; indicative credit restated as an executed fill; wrong Account/underlying; omitted stale/qualified status; unsupported action advice without new numbers. The $43.50 arithmetic can be numerically correct while the opening-credit or management-policy implication remains unsupported.

### D. Resolve disclosure before exposure, including experiments

Before protected data enters any model request, session store/replay, compaction request, trace exporter, debug log or hosted tool, establish the permitted data categories, destination, identity/context scope, retention and approved configuration. Apply the profile before crossing the boundary, including failure and retry paths. Unknown permission fails closed for that disclosure. Existing scoped permission is reusable only where its material assumptions still hold; do not require ZDR/MAM as an invented universal prerequisite.

Use native facilities where suitable, but evaluate inference storage, local history, provider-managed conversation state, compaction and tracing separately. `store:false` does not disable SDK trace export. A local session can still feed history into later inference or remote compaction. An output guardrail cannot undo disclosure that occurred earlier. Test configured production-like runtime behavior: Node tracing defaults differ from test-runtime defaults. Treat exception paths, custom processors and supplemental guardrail-model calls as disclosure paths too.

Bind conversation/session access to the authenticated User and intended context. Prior model history or a discovered tool never grants current authority. A new User, grant change or resume must not replay protected context outside permitted scope; solution design must define the applicable behavior rather than assume SDK sessions perform backend grant enforcement. Multi-user deployment is not authorized by requiring isolation-aware design.

### E. Keep fitness proportional and preserve early Product feedback

“Begin observational” applies to proposed architecture fitness controls and their delivery-system promotion. It does not defer already-required runtime authorization, permitted disclosure or trusted financial boundaries. Separate protocol correctness, semantic correctness and conversational usefulness; green results in one do not prove the others.

Use the existing small work-item proof index for specimen, invariant, result, exact version/configuration and unresolved limit. Validate proposed checks with conforming/nonconforming exemplars; record interpretation owner and a review/retirement condition before promotion. Observe time to first runnable specimen and Principal-visible result, integration changes, latency/token cost and Principal interruptions where measurable. Do not impose numerical budgets without evidence/authority.

API, non-model MCP and full-host probes are diagnostic layers that may proceed incrementally alongside an early end-to-end slice. They are not a mandatory serial MCP-first stage, second-host gate or exhaustive hardening campaign before operator observation. Start with an authorized synthetic hello world if needed; it proves wiring, not financial/security acceptance.
