# Wheelwright API v2 — repository contract entry point

The authoritative machine-readable entry point is [the common OpenAPI 3.1.1 specification](../contracts/api-v2-direct-quote-acquisition-proposal.yaml). Its historical filename is retained. It references [Account/evidence schemas](../contracts/api-v2-account-evidence.json), [market subject selection](../contracts/api-v2-market-evidence-subjects.json), and the [foundational financial-domain module](../contracts/api-v2-foundational-portfolio.json). Resolve the local references; do not infer coverage from a filename, CLI command or generated HTML.

Humans and agents consume the same contract. Static Redocly HTML is a derived human presentation. Agents read repository OAS and linked Product/domain contracts directly; no HTML scraping, extra agent format, registry or MCP server is required.

The foundational module follows the [Principal-accepted domain baseline and mandatory corrections](../discovery/api-v2-specification-acceptance-checkpoint-2026-10-21.md), under the [full implementation handoff](../discovery/api-v2-full-implementation-handoff-2026-10-21.md). It replaces the alpha interpretation of Position identity with independent GUID resources and separately readable retained brokerage holdings. Construction instances and exact Model versions are immutable; read-only Orders, qualified evaluations, provenance and Account reconciliation remain client-independent. Portfolio membership, an Execution root and universal split/recombine policy remain deferred.

The isolated [implementation coverage and verification package](../implementation/api-v2-foundational-2026-10-21/README.md) distinguishes implemented behavior from remaining proof obligations. Operative source-contract inclusion does not declare complete API delivery, independent review, Product acceptance or publication. Existing publication identity metadata remains gated separately.

## Semantics and authority

- [Architectural guardrails](../77-api-v2-architectural-guardrails.md): backend ownership, authoritative OAS, security, errors, correlation, clocks, provenance, partial success, collection and read-through boundaries.
- [Quote acquisition](../contracts/api-v2-direct-quote-acquisition-proposal.md): explicit subjects, reuse/force, per-subject fulfillment, retained prior evidence and repeatability.
- [Held discovery](../contracts/api-v2-held-quotes-read.md) and [held instance](../contracts/api-v2-subject-show-held-quote.md): provider-free reads, complete committed representations, decoding, concurrency and missing evidence.
- [Accepted Account/evidence behavior](../cli/ww-account-evidence.md): stable IDs, artifact retention versus admission, source confidentiality and Position limitations.
- [Approved history checkpoint](../design/ww-history-approved-checkpoint-2026-10-15.md) and its linked Product design; [accepted integrated delivery](../design/ww-integrated-update-candidate-2026-10-15/README.md): nested history, bounded read-through, original evidence, source identity and incomplete/lifetime coverage limits.
- [Portfolio Capital](../foundations/portfolio-capital.md) and [accepted bounded history](../design/pl-cli-01-portfolio-capital-history.md): qualified composites and gaps.

Authentication, explicit grants and application configuration determine API availability to a caller. OAS advertises capabilities; it does not authorize an agent to invoke them. Current Principal/task authority separately governs operational acquisition, persistence, deployment and other consequential actions. Resource IDs confer no permission. Administrator User inspection grants no blanket financial access. Internal-only description blocks remain part of authoritative OAS and must be read with standard security requirements and `x-required-grants`.

The bounded [Product-conformance correction candidate](../implementation/api-v2-foundational-2026-10-21/product-conformance-2026-10-22/verification.md) corrects default holdings selection and page expansion, and improves public operation explanations/examples. Default holdings select each authorized Account's latest admitted cut, including qualified partial/empty cuts; `accountId` plus `snapshotId` selects retained history. Failed acquisition preserves prior admitted evidence. Financial collection pages retain Account-wide reconciliation even when details expand only the selected members. These candidate changes await independent verification before integration/publication.

Machine-readable grant extensions describe existing runtime requirements: `x-required-grants` is unconditional for the operation; `x-required-grants-when-force` adds requirements for quote mode FORCE; `x-required-grants-for-account-scope` adds the exact Account grant for private Account-scoped market observations (including resources discovered without an explicit Account query). They do not grant access or replace per-resource enforcement. All `x-required-grants*` instructions remain private to the authoritative projection. Framework unknown-route and unsupported-method failures under `/v2` use the common problem grammar with correlation; unsupported methods add405/METHOD_NOT_ALLOWED and Allow. Existing resource-level non-disclosure and legacy `/api` behavior remain separate.

Only accepted `/v2` operations are in this documentation product. Legacy `/api` and future web-client migration are outside its scope. Original specification-phase footers in linked contracts must be reconciled with their later accepted-delivery records; they are not independent current execution grants.
