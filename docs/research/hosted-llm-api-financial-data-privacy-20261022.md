## Executive findings

1. **The OpenAI API default is "no training, but 30 days of content logs" — not "nothing is kept."** Since 1 March 2023 API data is not used to train/improve models unless the customer explicitly opts in **[CONTRACTUAL COMMITMENT + DOCUMENTED TECHNICAL BEHAVIOR]**, but by default OpenAI generates abuse-monitoring logs that *may contain prompts and responses* and retains them **up to 30 days**, longer if required by law or reasonably necessary to protect the services/third parties. Source S1.
2. **Zero Data Retention (ZDR) and Modified Abuse Monitoring (MAM) are approval-gated, not settings you can simply switch on.** Both require prior OpenAI approval and acceptance of additional requirements, are configured per organization/project after approval, and ZDR only fully applies to endpoints marked eligible in OpenAI's table. Conversations, Agents, Assistants/Threads, Vector Stores, Files, Fine-tuning, Evals, Batch and Audio Voices are **not** ZDR-eligible and can retain application state **until deleted** even in a ZDR organization. **[OPTIONAL ENROLLMENT REQUIRED]** Source S1.
3. **Even under ZDR, things are still retained:** image/file inputs flagged by the CSAM classifier (retained for manual review *even under ZDR/MAM/Private Retention*), prompt-cache key/value tensors on GPU-local storage for up to 24 hours, background-mode data ~10 minutes, audio-output state 1 hour, system/billing/metadata (expressly outside data-residency and, by extension, content-retention promises), safety signals under Private Safety Processing (PSP), content in *customer-controlled* PSP storage with a 30-day lifecycle, and anything OpenAI is legally required to keep. OpenAI also *reserves the right* to move specific customers/models out of ZDR/MAM into "Private Retention" (encrypted logs, no human review unless law requires) or "Safety Retention" (retention **plus human review**) with advance written notice. Sources S1, S4, S5.
4. **Consumer ChatGPT is a different product with a different default — do not conflate them.** For individuals (Free/Plus/Pro), OpenAI *may* use content to train unless the user opts out ("Improve the model for everyone" off, or Privacy Portal), and even after opting out, giving thumbs-up/down feedback can put the *entire associated conversation* into training. Business/API data is not trained on by default; API org owners can *opt in* to data sharing, after which members can share feedback and Playground chats. Source S8.
5. **Cross-customer exposure is contractually and architecturally addressed, but not independently proven, and it has happened in the adjacent consumer product.** The Services Agreement bars use of Customer Content except to provide the service/comply/enforce/prevent abuse and bars combining CCPA customer data with other parties' personal data (DPA); prompt caches are documented (2024 announcement) as not shared between organizations, and the current caching guide stores KV tensors, not tokens, scoped by routing within an organization/region. However, in March 2023 a redis-py bug in **ChatGPT** (OpenAI's postmortem does **not** say the API was affected) let some users see other users' chat titles/first messages and exposed payment-related data of ~1.2% of active ChatGPT Plus subscribers in a 9-hour window. Model memorization of *training* data is independently demonstrated research (Carlini et al., GPT-2) — which is precisely why the no-training-on-API-data commitment matters, and why it does not eliminate regurgitation of data the model was legitimately trained on. Sources S13, S27, S28, S6.
6. **Legal process is a demonstrated, not hypothetical, residual risk.** In 2025 a court order in the NYT litigation forced OpenAI to retain consumer ChatGPT **and API (non-ZDR)** content indefinitely; the order's obligations ended 26 September 2025, but a limited set of April–September 2025 historical data is still held under legal hold, accessible only to a small audited legal/security team. ZDR customers and ChatGPT Enterprise/Edu were not impacted. Source S14.
7. **For sensitive personal financial data, the defensible OpenAI configuration is narrow:** an approved ZDR (or at minimum MAM) organization/project, only ZDR-eligible stateless endpoints (Chat Completions / Responses with `store` forced false, Embeddings, Moderations, Realtime, transcription), no Files/Vector Stores/Conversations/Agents/Batch/Evals/Fine-tuning with real personal data, no live Web Search, third-party MCP/tools treated as separate processors, data minimization/redaction before the call, and a signed DPA (and BAA only if PHI is in scope). Anything outside that envelope reintroduces retention-until-deleted or third-party retention. **[APPLICATION RESPONSIBILITY]**
8. **Alternatives differ mainly in *who* holds the data and *how* ZDR is achieved, not in the headline "no training" claim** — all of Azure OpenAI, Anthropic commercial API, Google Vertex AI (and paid Gemini API), and AWS Bedrock contractually/documentedly do not train on customer content. The meaningful differences: Azure OpenAI data is processed by **Microsoft, not OpenAI**, with CMK and a portal-verifiable abuse-monitoring off switch; Anthropic's ZDR now has a **Covered Models carve-out** (Fable/Mythos-class: mandatory 30-day retention since 9 June 2026); unpaid Gemini API **does** use content to improve Google products with possible human review — never use it for personal data; Bedrock keeps content inside AWS with model providers having no access to deployment accounts/logs, but some models now require retention/`aws_review` as a condition of access. See §11 table.
9. **Contradictions found in OpenAI's own current pages (preserved, §2/§8):** (a) the Your Data table lists Chat Completions application state as "None," while the migration guide says "Chat completions are stored by default for new accounts"; (b) the same table lists Responses application state as "None, see exceptions," while the exception text says Responses data is stored **at least** 30 days by default/when `store=true`; (c) the current DPA's subprocessor-change notice has no advance-days commitment in the text read, whereas older DPA copies said 15 days' notice.

## Findings

### 1. Training use — API vs ChatGPT consumer, opt-in/opt-out, fine-tuning, feedback

**OpenAI API — no training by default. [CONTRACTUAL COMMITMENT]**
- "As of March 1, 2023, data sent to the OpenAI API is not used to train or improve OpenAI models (unless you explicitly opt in to share data with us)." — Data controls page (S1, no date shown).
- Enterprise privacy page (S2, updated 8 Jan 2026): "We do not train our models on your data by default" for API + ChatGPT Business/Enterprise/Edu/Healthcare/Teachers; business-data page (S3) adds training happens only via "explicit opt-in in the API dashboard."
- Services Agreement §4.2 (hosted copy, S27): OpenAI will only use Customer Content as necessary to provide the Services, comply with law, enforce policies and prevent abuse; it "will not use Customer Content to develop or improve the Services, to train any models (**except for fine-tuning, embeddings, and similar activities conducted solely for the benefit and use of Customer**), or otherwise for commercial advantage unless Customer explicitly agrees."
- Help Center (S8): "API organization owners can enable data sharing. When they do, members can choose to share **feedback and the current API Playground chat** to help improve OpenAI models." So the API opt-in surface is: org-owner data-sharing toggle + per-member feedback/Playground sharing. **[OPTIONAL ENROLLMENT REQUIRED — in reverse: training only after opt-in]**

**Fine-tuning data. [CONTRACTUAL COMMITMENT / DOCUMENTED TECHNICAL BEHAVIOR]**
- Fine-tuning is the carve-out above: data you submit to fine-tune is used to train *your* custom model, solely for your benefit/use. Your Data table: `/v1/fine_tuning/jobs` — training use "No" (i.e., not for OpenAI's general models), application state **until deleted**, not ZDR-eligible (S1). Enterprise privacy (S2): "Custom models are yours alone to use and are not shared with anyone else." The older API Platform FAQ (via search index of the 2024 enterprise-privacy PDF) likewise said fine-tuned models are "for your use alone and never served to or shared with other customers or used to train other models," with fine-tuning data retained until the customer deletes the files — consistent with S1, but that PDF is an older snapshot; treat S1 as controlling.

**ChatGPT consumer — opposite default. [CONTRACTUAL COMMITMENT — consumer terms/help]**
- Help Center (S8, "Updated: 3 days ago" as shown): "When you use our services for individuals (Free, Plus, Pro), we may use your content to train our models." Opt out via Settings > Data controls > "Improve the model for everyone" off, **or** Privacy Portal "Do not train on my content"; either suffices; after opt-out, *new* conversations are not used.
- **Feedback exception (consumer):** "Even if you have opted out of training… If you choose to provide feedback… the entire conversation associated with that feedback may be used to train our models." For Business/Enterprise/Edu, by contrast, thumbs up/down "does not permit training on the associated conversation" absent a separate agreement (S8).
- **Temporary chats** are not used to improve models while they remain temporary and don't create memories; if saved, they become regular chats under the account's settings (S8). Per S14, deleted/temporary consumer chats are scheduled for deletion within 30 days, subject to legal/security retention.
- **Flag:** Do not cite consumer ChatGPT policy as evidence about the API, or vice versa. They differ on default (opt-out vs no-training), on DPA availability (no DPA for consumer service), and on retention controls.

### 2. What data is retained, for what purposes, for how long

OpenAI's own framing (S1) splits API storage into exactly two buckets — everything else (billing, account, metadata) sits outside that framing and must be asked about separately:

| Category | What it contains | Default retention | Label |
|---|---|---|---|
| **Abuse-monitoring logs** | Logs of platform use to enforce Usage Policies/agreements and mitigate harmful use; "may contain certain customer content, such as prompts and responses, as well as metadata derived from that customer content, such as classifier outputs" | **Up to 30 days** for all API features by default, "unless longer retention is required by law, or is reasonably necessary to protect our services or any third party from harm" | DOCUMENTED TECHNICAL BEHAVIOR |
| **Application state** | Data persisted by a feature to fulfil the task (responses, conversations, files, vector stores, threads, batches, evals, fine-tuning jobs…) | Endpoint-specific — see §4 matrix. Ranges from *none*, to 30 days, to **until deleted / indefinitely if never deleted** | DOCUMENTED TECHNICAL BEHAVIOR |
| **Prompt cache** | Encrypted key/value (KV) tensors — "not the tokens themselves" (S9) — in GPU-local storage | Up to **24 hours** maximum application-state retention per S1; in-memory mode typically 5–10 min inactivity, up to 1 hour (S9) | DOCUMENTED TECHNICAL BEHAVIOR |
| **System data** (account, metadata, usage, billing, support, structured-output schema) | Defined in the data-residency section of S1: "account data, metadata, and usage data that do not contain Customer Content… such as account information… analytics, usage statistics, billing information, support requests, and structured output schema" | **No duration stated on the page read.** Data residency expressly does not apply to it; it "may be processed and stored outside the selected region" | UNKNOWN—REQUIRES CUSTOMER CONFIRMATION (duration) |
| **Safety-system retention** | CSAM-flagged images/files; content under Safety Retention / Private Retention carve-outs; PSP safety records in customer storage | CSAM: retained for manual review, no duration stated (S1). PSP customer-storage records: 30-day lifecycle rule the *customer* must set (S5). Safety/Private Retention: see §3/§5 | DOCUMENTED TECHNICAL BEHAVIOR |
| **Legal holds** | Content subject to court order / legal requirement | The 2025 NYT order: indefinite while in force (ended 26 Sep 2025 for new data); limited Apr–Sep 2025 historical set still held, legal-use only (S14). DPA §2.11: data required by law is isolated and protected from further processing except as legally required (S6) | CONTRACTUAL COMMITMENT + documented incident |
| **Deleted application-state objects** | Assistants/Threads/Vector Stores objects deleted via API/dashboard | Deleted from servers **30 days after you delete them**; objects never deleted are "retained indefinitely" (S1) | DOCUMENTED TECHNICAL BEHAVIOR |
| **Files** | `/v1/files` objects | Until deleted manually or via `expires_after` (S1) | DOCUMENTED TECHNICAL BEHAVIOR |
| **DPA-level commitment** | API Service Customer Data | Current DPA (S6, effective 1 Jan 2026) governs return/deletion on termination: at customer instruction, return or delete, unless law requires retention (isolate/protect). *Note:* older DPA copies circulating in search results stated a flat "maximum of thirty (30) days" for API data — that sentence was **not** in the current DPA text read; the 30-day figure today lives in the developer documentation (S1) and S14 ("After 30 days, API inputs and outputs are removed from OpenAI logs, unless we are legally required to retain them"). **Contradiction/ drift preserved:** do not quote the old DPA sentence as current. | CONTRACTUAL COMMITMENT |

**Purposes** for retention, as documented: abuse/policy enforcement and harm mitigation (abuse logs); fulfilling the feature's function (application state); legal compliance; service protection. Training is *not* a stated purpose for API logs (see §1).

### 3. Standard vs Modified Abuse Monitoring (MAM) vs Zero Data Retention (ZDR)

|  | **Standard (default)** | **Modified Abuse Monitoring (MAM)** | **Zero Data Retention (ZDR)** |
|---|---|---|---|
| Training use | No (unless opt-in) | No (unless opt-in) | No (unless opt-in) |
| Customer content in abuse-monitoring logs | Yes — may include prompts/responses + derived metadata | **Excluded** across **all** API endpoints (exception: image/file inputs in rare CSAM cases, §5) | **Excluded**, same as MAM |
| Application state | Endpoint default (Responses stored by default; stateful objects until deleted) | **Unchanged** — "still allowing the customer to take advantage of the full capabilities of the OpenAI platform"; stateful endpoints still store state | `store` for `/v1/responses` and `/v1/chat/completions` **always treated as `false`** even if set `true`; ZDR-eligible endpoints retain no application state; **ineligible endpoints may still store application state even with ZDR on** |
| Eligibility / approval | Default for all API customers | "Subject to prior approval by OpenAI and acceptance of additional requirements"; contact sales (S1) | Same approval gate as MAM (S1) |
| Configuration once approved | — | Data Retention tab in Settings → Organization → Data controls; choose MAM or ZDR at org level; per project: `default` (inherit), explicit MAM/ZDR, or **None** (disables controls for that project) (S1) | Same |
| Customer obligations added | — | Customer responsible for ensuring its users abide by OpenAI policies and for complying with moderation/reporting requirements under applicable law (S1) | Same |
| BAA / residency linkage | — | Non-US data residency requires approval for abuse-monitoring controls **and** a Modified Retention amendment (S1) | Same; Web Search offline mode is BAA-eligible only from a ZDR project in a ZDR org (S1) |
| Verification available to customer | Dashboard/logs show stored responses | **[UNKNOWN]** — no customer-facing verification mechanism for MAM/ZDR is described on S1 beyond the settings tab showing the selected policy | Settings tab shows policy; PSP guide shows "Storage validated" + project policy confirmation for ZDR-with-PSP (S5) |

**Two 2026 variants that qualify the ZDR/MAM promise (S1) — read these before relying on either:**
- **Private Retention with PSP (formerly "Eyes Off"):** For ZDR/MAM-approved customers, OpenAI "reserve[s] the right to make models ineligible for Zero Data Retention or Modified Abuse Monitoring for specific customers, as notified in advance… in writing. In this instance, customer content will be retained in encrypted abuse monitoring logs in OpenAI-managed infrastructure, but such content will be excluded from human review unless required by applicable law." BAA customers provisioned with it can still use BAA-eligible endpoints for PHI.
- **Safety Retention:** Same reservation, triggered "if reasonably necessary to investigate or prevent severe risk activity": OpenAI "may retain **and human review** customer content… that our classifiers detect as potentially violating" policies/agreement.
- **ZDR with Private Safety Processing (PSP):** **[OPTIONAL ENROLLMENT REQUIRED]** Automated cross-interaction safety monitoring designed to preserve ZDR: content stays on **customer-controlled storage** (AWS S3 / Azure Blob / Google Cloud Storage, per-project, with a customer-set 30-day lifecycle rule; S5), or a still-in-development option of OpenAI storage encrypted with customer-controlled keys (S4). OpenAI receives only "a narrowly defined signal indicating the type of activity"; personnel do not get the content even when flagged; customers investigate themselves and may voluntarily share content to appeal (S4). Announced/previewed 19 Aug 2026; update 22 Sep 2026 says rollout to API customers is proceeding in phases (S4). Whether the PSP architecture has been independently audited: **UNKNOWN—REQUIRES CUSTOMER CONFIRMATION** (a technical whitepaper is referenced from S1; no independent assessment was found in this research).

### 5. What may STILL be retained even under ZDR

1. **CSAM-flagged images/files — retained for manual review.** "Image and file inputs are scanned for CSAM content upon submission. If the classifier detects potential CSAM content, the image will be retained for manual review, **even if Zero Data Retention, Modified Abuse Monitoring, or Private Retention with PSP is enabled**." (S1) **[DOCUMENTED TECHNICAL BEHAVIOR]** The ZDR announcement's "content is not available to OpenAI personnel for review" promise carries footnote 1 for exactly this exception (S4, footnote text via secondary reporting).
2. **Application state on ZDR-ineligible endpoints/capabilities** — everything marked **No** in §4 "may still store application state, even if Zero Data Retention is enabled" (S1): conversations, agents, assistants/threads, vector stores, files, fine-tuning, evals, batches, audio voices — generally **until you delete them** (Assistants-family objects: deleted from servers 30 days *after* you delete them; never-deleted objects retained indefinitely).
3. **Prompt-cache KV tensors** — encrypted KV tensors in GPU-local storage, "not retained after the 24-hour expiration" (S1); ZDR orgs *default* to `in_memory` cache retention on models that support both modes (S9), but extended/24h behaviour is model-dependent — verify per model.
4. **Transient feature state:** background-mode response data ~10 min on disk for polling; audio-output state 1 hour; hosted-container filesystem contents while the container is active (S1).
5. **Metadata / system data:** account, usage, billing, support, analytics and schema data are defined separately from Customer Content (S1 residency section) and no ZDR statement read covers them. The PSP design likewise leaves OpenAI an index of "operational metadata and a reference to the stored record" rather than the content (secondary description of the PSP whitepaper, Automater/VentureBeat reporting on S4/S5 — label: **DOCUMENTED TECHNICAL BEHAVIOR as described by vendor + secondary; whitepaper itself not independently assessed here**).
6. **Safety signals under PSP:** when PSP flags activity, OpenAI receives a "narrowly defined signal" (category/severity-type information) — the signal is retained by OpenAI even though content is not (S4).
7. **PSP safety records in customer storage:** content selected by a safety classifier or an approved sampling policy is encrypted into *your* S3/Azure Blob/GCS bucket with the 30-day lifecycle **you** configure (S5). ZDR-with-PSP therefore does not mean "no copy exists anywhere" — it means the copy lives under your control. **[APPLICATION RESPONSIBILITY to configure the lifecycle correctly]**
8. **Private Retention / Safety Retention carve-outs:** OpenAI reserves the right, with advance written notice to the affected customer, to make models ineligible for that customer's ZDR/MAM — resulting in encrypted-log retention (Private Retention) or retention **plus human review** (Safety Retention) (S1). This is a contractual reservation, not a hypothetical.
9. **Legally required retention / legal holds** — DPA §2.11 and S1's "unless longer retention is required by law" language apply under every tier, including ZDR (though the 2025 court order expressly did **not** reach ZDR data because it was never stored, S14).
10. **Flagged-content sharing with moderation subprocessors (standard/MAM context):** the subprocessor list (S7) says that for content flagged as violating policy, OpenAI "may share samples of the flagged Customer Content with relevant Sub-processors to assist… in review and enforcement," retained by the subprocessor only for the review period. Snowflake and Cinder entries carry "* Except where Zero Data Retention (ZDR) is used" — implying those two do not process ZDR customer data; TaskUs/Accenture moderation entries carry no such asterisk. **[UNKNOWN—REQUIRES CUSTOMER CONFIRMATION]** exactly which moderation subprocessors can see flagged content from a ZDR/MAM org.

### 6. Encryption, access, isolation, subprocessors, DPA, certifications, BAA/GDPR, residency

- **Encryption in transit / at rest. [DOCUMENTED TECHNICAL BEHAVIOR / CONTRACTUAL-adjacent]** AES-256 at rest, TLS 1.2+ in transit between customer↔OpenAI and OpenAI↔its service providers (S2, S3, S12). For `us.api.openai.com` / `eu.api.openai.com`, TLS termination and HTTPS decryption occur inside the selected processing region via Cloudflare Regional Services (S1, S7).
- **Customer-managed keys — Enterprise Key Management (EKM). [OPTIONAL ENROLLMENT REQUIRED]** EKM lets you encrypt customer content at OpenAI with keys in *your* external KMS (BYOK supported: AWS KMS, Google Cloud KMS, Azure Key Vault; other KMSs must be synced to one of those). EKM applies to application state created on the platform. **Limitations (S1):** projects with EKM enabled **error** on Assistants (`/v1/assistants`) and vision fine-tuning. ### 7. Can one customer's data become visible to another customer, or appear in another's outputs?

**Contractual assurances [CONTRACTUAL COMMITMENT]:**
- Services Agreement §4.2 (S27): use of Customer Content limited to providing the service, legal compliance, policy enforcement, abuse prevention; no development/improvement/training (outside customer-only fine-tuning/embeddings) without explicit agreement.
- DPA §5.1(d)(iii) (S6): for CCPA data, OpenAI will not "combine any Customer Data with Personal Data that OpenAI receives from or on behalf of any other third party or collects from OpenAI's own interactions with individuals," except as directed/permitted.
- Fine-tuned/custom models "are yours alone… not shared with anyone else" (S2).
- Similarity caveat (§4.4, S27): "Output may not be unique, and other users may receive similar content" — similar ≠ your data, but it contractually normalizes non-unique outputs.

**Documented technical behaviour [DOCUMENTED TECHNICAL BEHAVIOR]:**
- **No training on API data by default** (S1) removes the main channel by which one customer's API inputs could be baked into a shared model and later regurgitated to others. API models are versioned/frozen artifacts, not continuously retrained on live traffic (per OpenAI's 2023 clarification, secondary S29).
- **Prompt caching scope:** the cache stores KV tensors, not tokens (S9). OpenAI's prompt-caching announcement (2024, via search index, S10) states: "Prompt caches are not shared between organizations. Only members of the same organization can access caches of identical prompts," with caches typically cleared after 5–10 minutes' inactivity and always within one hour — note the *current* guide (S9) describes longer retention modes (in-memory up to 1h; 24h extended; GPT-5.6+ TTLs of 30 min/12 h minimum lifetimes) and does **not** repeat the organization-sharing sentence in the text extracted; it instead documents routing "within an organization and processing region" and recommends a distinct `prompt_cache_key` per customer/user in your own application, partly because separate keys "help prevent cache-hit probing across users" — i.e., within your organization, a cache hit can act as a side-channel revealing that an identical prefix was recently sent. Discount mechanics today (S9): cache reads at 0.1× the uncached input rate on most GPT-5.6+ models (0.05× on GPT-6.1 Sol), writes at 1.25× (30-min TTL) or 2.5× (12-h TTL, Responses only); earlier models had different (often 50%) discounts and no write charge. **Within-org cache-hit probing is a real, documented side-channel; cross-org sharing is denied by the vendor.**
- **Memorization/regurgitation research (independent):** Carlini et al. (S28) extracted hundreds of verbatim sequences — including PII (names, phone numbers, emails), code and UUIDs, some present in only a single training document — from GPT-2, and found larger models more vulnerable. 2023 follow-on work (secondary summaries, S28 search results) extracted training data from production ChatGPT via a divergence attack. Implication, carefully scoped: this demonstrates what models can do with data they were **trained on** (public/licensed corpora). It is **not** evidence that OpenAI API inputs leak into other customers' outputs, because API inputs are not trained on by default. It *is* evidence that (a) anything you allow to be trained on (consumer feedback, opt-in data sharing, your own fine-tune that you then expose broadly) should be treated as potentially extractable, and (b) a model may regurgitate *someone else's* memorized training data into your outputs — a downstream data-quality/contamination risk for financial records.

**Documented cross-customer incident [documented incident — consumer product]:**
- **March 2023 ChatGPT outage (S13, OpenAI postmortem, no date shown on page; event 20 Mar 2023):** a bug in the open-source redis-py client corrupted pooled connections after cancelled requests, so a response "can receive data left behind… even if it belongs to another user." Effects: some users saw **titles of another active user's chat history** and possibly the **first message** of a newly created conversation; separately, payment-related information of **1.2% of ChatGPT Plus subscribers active in a 9-hour window** (1–10 a.m. PT, 20 Mar) could be visible to another active user — first/last name, email, payment address, card type, last four digits and expiry; "full credit cards numbers were not exposed at any time." Some subscription-confirmation emails were also misaddressed. OpenAI says it notified affected users, patched the library with the Redis maintainers, and (per secondary coverage) added redundant checks that cache-returned data matches the requesting user.
- **Was the API affected?** The postmortem (S13) describes ChatGPT, its chat-history feature and ChatGPT Plus subscription flows only. **No statement in the sources read says API customer content was exposed, and none says it was investigated and cleared either.** Accurate formulation: *the documented cross-customer incident was in consumer ChatGPT; no API cross-customer exposure incident was found in the sources researched.* **[UNKNOWN — whether OpenAI has ever had an unpublicized API-side incident cannot be established from public sources]**
- **Bug bounty / trust center:** S11 confirms a Bug Bounty Program (safe harbor, cash rewards via Bugcrowd) and a Trust Portal where the SOC 2 report can be requested. These support — but do not independently prove — the isolation claims; the SOC 2 Type II examination is the one item in this section that is **independently verified** (by the examining auditor, for the controls and period in the gated report — which this research could not read).

**Bottom line for §7:** cross-customer visibility via the API is (i) contractually prohibited in use/combination, (ii) architecturally denied for training and prompt caches, and (iii) not documented to have occurred in the API; but the strongest guarantees are **contractual + attested (SOC 2)**, not publicly reproducible technical proof, and the 2023 incident shows OpenAI's own stack has produced exactly this failure class in an adjacent product.

### 8. Tool calls, conversation history, stored responses, prompt caching, application state

- **Responses API `store` — CONTRADICTION PRESERVED.** Migration guide (S15, no date shown): "**Responses are stored by default.** Chat completions are stored by default for new accounts. To disable storage in either API, set `store: false`." Your Data page (S1): table lists Responses *and* Chat Completions application state as "None, see below for exceptions," then the Responses exception says the API "has a 30 day Application State retention period by default, or when the `store` parameter is set to `true`. In those cases, response data will be stored for **at least** 30 days." A secondary developer source (Raif docs) asserts Chat Completions `store` defaults to `false` — directly contrary to S15's "stored by default for new accounts." **Operational rule regardless of which sentence is right for your account vintage: always send `store:false` explicitly for sensitive data, and verify in the project dashboard/logs.** Under ZDR, `store` is forced `false` (S1, S15); ZDR orgs can use encrypted reasoning items (`encrypted_content` decrypted in memory, discarded, re-encrypted for return) to keep multi-turn reasoning stateless (S15).
- **Conversations API:** persists conversation state "as a long-running object with its own durable identifier… across sessions, devices, or jobs," storing messages, tool calls and tool outputs (Conversation state guide, index, S16). In the retention table (S1) `/v1/conversations` and `/v1/conversations/items` are **until deleted** for *both* abuse monitoring and application state, and **not ZDR-eligible**. Using Conversations with financial personal data is a deliberate decision to store that data at OpenAI until you delete it. **[APPLICATION RESPONSIBILITY]**
- **Assistants/Threads/Vector Stores:** application state until deleted; after *you* delete, OpenAI deletes from its servers within a further 30 days; never-deleted objects are retained indefinitely (S1). File Search necessarily rides on these stores.
- **Files / Batch / Evals / Fine-tuning:** all until deleted, none ZDR-eligible (S1). Batch input/output files, eval datasets and fine-tuning files are therefore persistent copies of whatever you upload — for financial data, each is a separate data store to inventory, expire (`expires_after` for files) and delete.
- **Prompt caching (S9, S1):** enabled by default for supported models. It caches the model's *full rendered context* — OpenAI-provided instructions, developer messages, tool definitions **and conversation history containing text, images, documents and supported audio** — as KV tensors. Retention modes: `in_memory` (typically 5–10 min inactivity, max ~1 hour) vs `24h` extended (typically ~30 min, up to 24 hours). Defaults by org policy on dual-mode models: **non-ZDR orgs default to `24h`; ZDR orgs default to `in_memory`** — except GPT-5.5/5.5-pro, which support `24h` only (setting `in_memory` errors). GPT-5.6+ uses `prompt_cache_options.ttl` (`30m` default minimum lifetime; `12h` in Responses) — a *minimum* lifetime, not a deletion deadline: "OpenAI may retain entries longer than the requested minimum." No manual cache clearing exists. S1 caps prompt-cache application state at 24 hours — reconcile that cap with the 12-h-minimum TTL before assuming deletion timing on GPT-5.6+. **[UNKNOWN — exact max retention for GPT-5.6+ 12h-TTL entries; REQUIRES CUSTOMER CONFIRMATION]**
- **Tool calls & third-party egress (S1):** "MCP servers… are third-party services, and data sent to an MCP server is subject to their data retention policies." "Data transmitted to third-party services over network connections is subject to their data retention policies." Function/tool arguments are chosen by the model from your context — anything in context (including financial personal data) can be placed into a tool call to *your own* functions (your logs then hold it) or to remote MCP/web-search providers (their policies then hold it). Web Search additionally sends query content derived from the conversation to a search backend. **[APPLICATION RESPONSIBILITY: allowlist tools, strip personal data from tool arguments, contractually cover every tool provider as a (sub)processor]**
- **Hosted tools' local state:** Code Interpreter/Hosted Shell containers can hold files/state on ephemeral block storage until container expiry/deletion (S1). Hosted Skills follow the same lifecycle.
- **Your own history resending:** in Chat Completions and manual Responses state management, *your application* resends the accumulated transcript every turn (S15) — so the full history traverses and is processed on every call, is covered by that call's abuse-log/cache behaviour, and usually also sits in your own logs/traces. Minimizing what you resend is a privacy control, not just a cost control.

### 9. Residual risks even when the provider does not train on inputs

1. **Prompt injection / exfiltration [APPLICATION RESPONSIBILITY].** OWASP LLM Top 10 (2025, via secondary summary S30): LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM05 Improper Output Handling, LLM06 Excessive Agency. Untrusted content the model reads (documents, web pages, tool outputs, other users' records in a shared context) can induce it to disclose data in context or call tools. A concrete secondary report (PromptArmor, Aug 2026) describes exfiltration via insecure Markdown-image rendering in OpenAI's *API logs UI* — i.e., the developer viewing logs becomes the exfiltration channel. Provider no-training promises do nothing against any of this.
2. **Provider breach / insider.** Any retained copy (30-day abuse logs, application state, PSP customer-storage, legal-hold sets) is breach surface; ZDR shrinks but does not zero it (§5). Insider risk is mitigated by confidentiality/access controls that are, for standard API logs, only described in gated documents (§6 gap).
3. **Subpoena / legal process / government access [documented].** The NYT order (S14) compelled indefinite retention of non-ZDR API + consumer content for months and production fights continue over a limited historical set; DPA §2.2 promises notice of law-enforcement requests only "to the extent legally permitted" (S6) — gag orders can lawfully prevent notice. Data you never send, or send only under ZDR, cannot be produced from OpenAI — S14 confirms ZDR data was out of scope *because it was not stored*.
4. **Logging at intermediaries.** Cloudflare TLS termination (regionally pinned for us/eu endpoints, S7), cloud infrastructure subprocessors (Microsoft/CoreWeave/Oracle/GCP/AWS/Cerebras), your own API gateways, observability/tracing tools, SDK debug logs, and the OpenAI dashboard's stored-completion logs are all additional copies/processors. Each needs its own retention setting.
5. **Endpoint / account compromise.** A leaked API key exposes your project — including any stored responses, files, vector stores and fine-tunes in it — and lets an attacker run up usage and submit data under your retention configuration. Key scoping/rotation is application responsibility (§10).
6. **Model output leakage into downstream logs.** Outputs frequently echo or infer input personal data; if your application logs outputs (support tools, analytics, eval pipelines), you have recreated the retention problem on your own infrastructure, outside any provider ZDR.
7. **Inaccuracy / financial-advice suitability.** Services Agreement §4.3 (S27): the customer "is solely responsible for all use of the Outputs and for evaluating the accuracy and appropriateness of Output for Customer's use case." Gemini's terms similarly make the customer responsible for generated content. Hallucinated figures, stale market facts, and confident misinformation (OWASP LLM09) in a financial context create suitability/conduct risk that no privacy control addresses; regulated financial advice requires human review, sourcing, and record-keeping by the firm, not the model provider. **[APPLICATION RESPONSIBILITY]**
8. **Availability / deprecation / price-change lock-in.** Documented in sources read: the Videos API was shut down (24 Sep 2026, S1); fine-tuning access was being wound down for many orgs during 2026 (secondary pricing coverage); data-residency pricing gained a 10% uplift for newer models (S1); Anthropic's Covered-Models change (§11) shows a provider can *change retention terms for new model classes* mid-relationship. Pin model snapshots, keep an exit/multi-provider plan, and re-verify retention terms at each model upgrade. **[APPLICATION RESPONSIBILITY]**
9. **Safety-system false positives.** Financial content (fraud discussions, sanctions screening, debt, crypto) can trip classifiers — under Standard/MAM that can mean human-review exposure of flagged samples (incl. to moderation subprocessors, S7); under Safety Retention it can mean retention + human review (S1).
10. **Jurisdiction mismatch.** Residency pins *content at rest*, not system data, not your end-users' locations, not third-party tools (§6) — a "EU residency" claim that ignores those exclusions overstates the protection.

### 10. Application-side controls before sending sensitive financial data (concrete checklist)

*Provider-configuration verification*
- [ ] Confirm in writing (order form / amendment / console screenshot) which retention tier the **specific org and project** is on: Standard / MAM / ZDR / ZDR+PSP / Private or Safety Retention. Do not infer from plan name. In the console: Settings → Organization → Data controls → Data Retention tab shows org policy and per-project override (`default`/explicit/**None**) (S1). Audit every project — one project set to **None** silently drops the org's controls for that project's traffic.
- [ ] Execute the DPA before sending personal data; execute a BAA only if PHI is in scope and only use BAA-eligible endpoints/configurations (S6, S11, S1). Record subprocessor-list subscription (email notifications) and an objection calendar (30-day window, S6).
- [ ] If residency matters: create the project *in* the region, use the regional base URL, confirm the model/endpoint appears in S1's regional support table, and accept in writing that system data is excluded. Budget the 10% uplift where it applies.
- [ ] Decide EKM: if enabled, exclude Assistants and vision fine-tuning from the design (they error under EKM, S1).

*Request-level hygiene*
- [ ] Send `store:false` explicitly on every Responses **and** Chat Completions call for sensitive data (do not rely on defaults — §8 contradiction); avoid background mode for ZDR-sensitive work; avoid Conversations/Agents/Assistants/Files/Vector Stores/Batch/Evals/Fine-tuning for personal data, or, where unavoidable, set `expires_after`, and run a deletion job (remember: deletion completes up to 30 days later for Assistants-family objects, S1).
- [ ] Prompt caching: prefer `in_memory` where the model supports it; on GPT-5.6+ use explicit breakpoints so personal-data suffixes are not written to cache, keep the default 30-min TTL rather than 12-h for sensitive prefixes, and use a distinct `prompt_cache_key` per end-customer to reduce cache-hit probing (S9).
- [ ] Disable/avoid live Web Search for personal-data flows; if search is essential, treat query text as disclosed data. Allowlist MCP servers and tools; contract each as a processor; strip personal data from tool arguments by schema design (IDs/tokens only).

*Data minimization before the call [the single highest-value control]*
- [ ] Field allowlist per use case: send only fields the task needs. Never send raw card numbers, CVVs, full account credentials, government IDs, or passwords — no provider commitment makes that safe or necessary.
- [ ] Redact/tokenize direct identifiers (names, account numbers, emails, phone, addresses, DOB) with a deterministic vault/tokenization service you control; re-identify only inside your own boundary after the response returns. Run PII detection (NER/regex + allowlist validation) as a blocking gateway check, with a canary test suite.
- [ ] Pseudonymize case references; truncate histories; summarize rather than forwarding raw statements/transcripts where a summary suffices.

*Keys, access, logging*
- [ ] One project + restricted API keys per application/environment; service-account keys, not user keys, in production; spend/rate limits per key; rotation and immediate revocation runbook; keys only in a secrets manager, never in prompts, repos, or client apps (route browser calls through your backend — note Anthropic makes the same point for ZDR/CORS, S26).
- [ ] Your audit logging should record metadata only — timestamp, project, model, endpoint, token counts, retention tier, hash/canary ID — **not** prompt/output content. If content logging is unavoidable for debugging, encrypt it, access-control it, and give it a shorter TTL than the provider's.
- [ ] Human review gate for any output that will affect a customer's finances (payments, credit, advice, eligibility), with the model's output treated as an unverified draft (S27 §4.3).
- [ ] Pre-launch canary test: send a unique nonsense string under the production configuration, then check everywhere it could persist — provider dashboard/logs, your traces, vector stores, files list, PSP bucket — and record the result in the DPIA/vendor file.

*Contractual checklist (ask, and get answers in writing)*
- [ ] Retention tier + which endpoints in §4 you will use are eligible; CSAM/flagged-content and Safety/Private Retention reservations understood; subprocessor list + notice subscription; DPA (and BAA if relevant) executed; residency scope incl. system-data exclusion; EKM scope/errors; deletion SLAs incl. the post-deletion 30-day tail; breach-notice commitment ("without undue delay", S6); audit-report access (Trust Portal, once/year audit right, S6); model-deprecation notice and snapshot pinning; price-change terms for residency/caching; exit plan (data return/deletion on termination, S6 §2.11).

## Residual-risk list (summary)

1. 30-day abuse-log window (standard tier) containing full prompts/responses — breach, insider, and legal-process exposure for its whole life.
2. Retention-until-deleted application state (files, vector stores, conversations, batches, evals, fine-tunes) — persists indefinitely if deletion is not engineered.
3. CSAM/flagged-content retention and human review, including sharing flagged samples with moderation subprocessors — applies even under ZDR/MAM (CSAM) and standard tiers (flagged samples).
4. Vendor-reserved reclassification of your models/usage into Private Retention or Safety Retention (OpenAI) or Covered-Models retention (Anthropic) — ZDR is not immutable across model generations.
5. Legal compulsion: court orders have already overridden standard retention once (NYT, 2025); gag-ordered process may not be notifiable.
6. Prompt injection → in-context data disclosure and tool-mediated exfiltration; output rendering in dashboards/logs as an exfiltration channel.
7. Third-party egress via MCP servers, web search, and your own function tools — each inherits the third party's retention, outside any provider ZDR.
8. Prompt-cache side channels (within-org cache-hit probing) and cache retention that is a *minimum*, not a deletion deadline, on newer models.
9. Your own copies: application logs, traces, eval datasets, stored-completion dashboards — usually the largest and least-governed copy of the data.
10. Model inaccuracy in financial contexts; contractual responsibility for output accuracy sits with you.
11. Deprecation/price/terms drift: endpoints shut down, residency uplifts added, retention terms changed for new model classes — continuous re-verification required.
12. Key compromise: one leaked project key exposes all state stored in that project.
